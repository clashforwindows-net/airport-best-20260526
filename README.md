## 我们怎么分析这个市场

为了避免"拍脑袋说趋势"，本文用 4 个维度交叉验证：

1. **技术维度**：协议、传输、客户端演进（决定体验上限）
2. **供给维度**：机场数量、集中度、跑路率（决定选择风险）
3. **需求维度**：用户画像迁移、用途变化（决定买什么）
4. **价格维度**：套餐定价、流量单价（决定花多少钱）

> 交叉看才有意义：比如"协议在演进"是技术事实，"用户只在乎看剧"是需求事实，两者结合才能判断"某项新技术对你是否值得追"。

## 行业发展历程（时间线）

| 阶段 | 时间 | 标志 | 用户状态 |
|------|------|------|---------|
| 萌芽期 | 2015 前 | SS 单节点、小圈子 | 极客自用 |
| 工具期 | 2015-2018 | 订阅制出现、客户端成熟 | 普通用户入场 |

**关键拐点**：2021 年后"节点越多越好"叙事失效，用户开始为**特定场景能力**（游戏低延迟、回国专线、企业 SLA）付费，行业从"规模竞争"转向"场景竞争"。

## 市场规模估算

（以下为基于公开讨论与社区样本的**量级估算**，非精确统计，仅用于判断方向）

- 活跃机场数量：数百家，但头部约 20 家占据主要流量
- 用户规模：千万级存量，年新增趋稳
- 客单价：月付 15-50 元为主流，年付约 150-500 元
- 市场特征：**长尾高度分散**，新站每月有开有关，跑路率仍不低

> 判断：市场已从"增量狂奔"进入"存量精耕"，这意味着——老牌稳定机场溢价能力增强，新站必须用差异化（专线/场景）才能活。

## 竞争格局分析

### 三类玩家

1. **综合型老牌**（如覆盖全档位的 ClashVIP 类）
   - 优势：档位全、解锁稳、客服体系成熟
   - 打法：做"基准选项"，覆盖最广人群
   - 风险：创新节奏相对慢

2. **场景型专精**（游戏专线 / 回国 / 企业）
   - 优势：单点能力极致，黏性高
   - 打法：深耕一个画像，溢价能力强
   - 风险：人群天花板低

3. **价格型新站**
   - 优势：便宜、敢送流量
   - 打法：低价拉新
   - 风险：跑路率高，慎选

### 集中度判断

市场**未高度集中**，但用户用脚投票向"稳定+解锁强"的老牌聚集。结论：普通用户优先综合型老牌做基准，再按场景叠加专精机场，比全押新站安全。

## 用户需求变化

从社区反馈看，需求重心在迁移：

- **2019-2021**："能连上就行" → "速度快"
- **2021-2023**："节点多" → "流媒体全解锁"
- **2023-2025**："解锁" → "特定场景稳"（游戏低延迟、回国、企业）
- **2025-2026**："稳" → "省心"（客户端智能、少折腾、客服快）

> 一句话：用户从"要功能"走向"要体验"。这解释了为什么老牌综合机场靠"少折腾"重新吃香。

## 趋势不是感觉：5 个可量化信号与判断阈值

"行业在往哪走"最容易变成玄学。把它变成可测量的事，只需要 5 个能被你亲手采集的信号。下表给出采集方式与判断阈值 —— 这不是预测，而是**让预测有输入**。

| # | 信号 | 采集方式 | 观测周期 | 阈值/判读 | 含义 |
|---|------|---------|---------|----------|------|
| 1 | 协议采纳率 | 抽样 30 个机场订阅，统计 VLESS/Trojan/SS 出现比例 | 季度 | Reality 占比 >25% 即"已成主流" | 技术换代进度 |
| 2 | 流量单价 | 套餐价 ÷ 流量，取 3 家头部中位数 | 月 | 连续 3 月持平 → 触底 | 价格战是否结束 |
| 3 | 跑道率 | 随机 20 个新站，看 90 天后仍可访问比例 | 季度 | <50% → 淘汰加速期 | 供给端健康度 |
| 4 | 场景溢价 | 游戏/企业档单价 ÷ 通用档单价 | 季度 | >1.8 且上升 → 细分在赚钱 | 竞争转向哪 |
| 5 | 解锁波动 | 每周测一次 Netflix/Disney+ 可用性 | 周 | 连续 2 周下降 → 风控收紧 | 解锁权重是否该降 |

**为什么是这 5 个**：前 3 个描述"供给侧"，后 2 个描述"需求侧与风险"。行业分析最常见的错误，是只看技术新闻（协议）不看商业现实（单价、跑道率），结果得出"技术很先进所以值得买"的错结论。

## 供给端跑道率统计（Python，可直接跑）

跑道率（runway rate）是判断一个赛道是否健康最硬的指标：**新进入者有多少活过 90 天**。它比任何"行业分析报告"都真实，因为跑路是骗不了人的。

下面这个脚本用 HTTP 探测 + 历史快照，算出你关注的候选池跑道率。

```python
# runway.py —— 机场存活率/跑道率统计
# 依赖: pip install requests
import json, time, pathlib, datetime
import requests

SNAPSHOT = pathlib.Path("airport_snapshot.json")
TIMEOUT = 8

def probe(url: str) -> dict:
    """探测一个机场官网是否可用，返回状态与耗时"""
    t0 = time.time()
    try:
        r = requests.get(url, timeout=TIMEOUT, allow_redirects=True,
                         headers={"User-Agent": "Mozilla/5.0 (compatible; Probe/1.0)"})
        return {
            "ok": r.status_code == 200,
            "code": r.status_code,
            "ms": int((time.time() - t0) * 1000),
            "len": len(r.content),
        }
    except Exception as e:
        return {"ok": False, "code": None, "ms": None, "err": type(e).__name__}

def load():
    if SNAPSHOT.exists():
        return json.loads(SNAPSHOT.read_text(encoding="utf-8"))
    return {}

def save(data):
    SNAPSHOT.write_text(json.dumps(data, ensure_ascii=False, indent=2), encoding="utf-8")

def runway_rate():
    """统计首次记录 >=90 天且当前仍可用的比例"""
    data = load()
    today = datetime.date.today()
    old, alive = 0, 0
    for url, rec in data.items():
        first = datetime.date.fromisoformat(rec["first_seen"])
        if (today - first).days < 90:
            continue
        old += 1
        if rec.get("last_ok"):
            alive += 1
    return old, alive, (alive / old * 100 if old else None)

def main(targets: list[str]):
    data = load()
    today = datetime.date.today().isoformat()
    rows = []
    for url in targets:
        res = probe(url)
        rec = data.get(url, {"first_seen": today})
        rec["last_ok"] = res["ok"]
        rec["last_code"] = res.get("code")
        rec["last_ms"] = res.get("ms")
        rec["last_check"] = today
        rec.setdefault("history", []).append({"date": today, "ok": res["ok"]})
        data[url] = rec
        rows.append((url, res["ok"], res.get("code"), res.get("ms")))
    save(data)

    print(f"{'官网':<40} {'可用':<6} {'状态码':<8} 耗时")
    for url, ok, code, ms in rows:
        print(f"{url:<40} {'是' if ok else '否':<6} {str(code):<8} {ms}ms")

    old, alive, rate = runway_rate()
    if rate is None:
        print("\n[跑道率] 样本观察期不足 90 天，暂无结论（继续按周跑）")
    else:
        print(f"\n[跑道率] 观察满 90 天的样本 {old} 个，仍可用 {alive} 个 → {rate:.1f}%")
        if rate >= 70:
            print("判读: 供给端健康，新站存活率尚可，可适度尝试新站。")
        elif rate >= 50:
            print("判读: 淘汰期，新站风险中等 —— 主力仍应放在运营 1 年以上的老牌。")
        else:
            print("判读: 淘汰加速期，新站慎入，优先老牌 + 保留备用。")

if __name__ == "__main__":
    # 把你的候选池填进来（建议 15-30 个，覆盖老牌/新站/专精站）
    targets = [
        "https://clashvip.net",
        "https://nav.clashvip.net",
        "https://clashhub.net",
        # "https://example-new-airport.com",
    ]
    main(targets)
```

**怎么用这份数据**，有三条判读规则：

- **跑道率 ≥70%**：赛道健康，新站值得试，可以用"月付小额试错"的方式探索性价比。
- **50%-70%**：淘汰期。新站只能当"备选"，主力必须是运营满 1 年的老牌。
- **<50%**：淘汰加速期。此时的正确动作不是找更便宜的新站，而是**把主力收拢到抗波动能力强的综合型**，同时把"备用"从建议变成必需。

> 注意：跑道率只能统计"官网还能打开"。域名能开但服务已停的"僵尸站"会被误判为存活，所以脚本里同时记录 `len`（页面字节数）—— 首页缩水到几百字节通常意味着关停公告页。

## 流量单价指数：一把跨机场可比的尺子

"这家 55 元 500G，那家 30 元 200G，谁便宜？"大多数人的算法是错的，因为他们算的是"总价"，而不是"可用单价"。

**正确的算法：有效单价 = 套餐价 ÷ (流量 × 实际可用率)**

```python
# unit_price.py —— 有效流量单价指数
def effective_price(price, gb, usable_ratio=0.9, devices=3, need_devices=3):
    """
    price: 月价（元）
    gb: 套餐流量（GB）
    usable_ratio: 实际可用比例（0.85-0.95，受超售/限速影响）
    devices: 套餐设备数; need_devices: 你实际需要的设备数
    """
    if devices < need_devices:
        return None  # 设备数不够，价格不可比（需买两份）
    effective_gb = gb * usable_ratio
    return price / effective_gb

plans = [
    ("基础 100G/3设备", 15, 100, 0.90, 3),
    ("标准 300G/5设备", 35, 300, 0.90, 5),
    ("高级 500G/8设备", 55, 500, 0.92, 8),
    ("企业 1T/不限",    99, 1024, 0.95, 99),
]

print(f"{'套餐':<22}{'元/GB':>10}  排名")
ranked = sorted(
    [(n, effective_price(p, g, u, d)) for n, p, g, u, d in plans],
    key=lambda x: x[1]
)
for i, (name, up) in enumerate(ranked, 1):
    flag = "  <-- 单价最低" if i == 1 else ""
    print(f"{name:<22}{up:>10.3f}  #{i}{flag}")
```

输出会告诉你一个反直觉的事实：**大流量档的"元/GB"往往最低，但你可能根本用不完** —— 这时候"单价最低"反而是最贵的选择，因为你为没用的流量付了钱。

所以真正的指数要再加一层：**实付单价 = 套餐价 ÷ min(套餐流量, 你的实际月用量)**

| 你的月用量 | 买 100G（15 元） | 买 500G（55 元） | 谁更划算 |
|-----------|----------------|----------------|---------|
| 60 GB | 0.250 元/GB | 0.917 元/GB | 100G 档 |
| 100 GB | 0.150 元/GB | 0.550 元/GB | 100G 档 |
| 300 GB | 0.150 元/GB（超量另计） | 0.183 元/GB | 500G 档 |
| 500 GB | 不可用 | 0.110 元/GB | 500G 档 |

> 这张表才是"价格趋势"真正该看的东西：**价格在降，但"你的实付单价"取决于你用多少**。这也是为什么行业单价触底后，省钱的方式从"等降价"变成了"选对档位 + 年付锁价"。

## 协议生命周期表与技术采纳 S 曲线

协议不是越新越好，而是处在生命周期的不同阶段。买机场本质上是买"某个协议在它当前阶段的稳定性"。

| 协议 | 引入期 | 成熟期 | 当前阶段（2026） | 优势 | 主要代价 |
|------|-------|-------|----------------|------|---------|
| Shadowsocks | 2013 | 2017-2019 | 衰退/兼容层 | 极简、客户端全覆盖 | 抗识别弱，易被 QoS |
| VMess | 2017 | 2019-2021 | 衰退 | 生态广 | 特征明显、握手开销 |
| Trojan | 2019 | 2021-2023 | 成熟后期 | 伪装 HTTPS，兼容好 | 依赖真证书，特征仍在 |
| VLESS | 2020 | 2022-2025 | 成熟期 | 无加密冗余、轻量 | 需配合传输层 |
| VLESS+Reality | 2023 | 2025-2027 | 快速采纳期 | 免证书、抗主动探测 | 客户端/内核支持参差 |
| TUIC / Hysteria2 | 2022 | 2024-2026 | 快速采纳期 | 弱网/高丢包下极强 | UDP 被 QoS 时失效 |
| WireGuard 类 | 2018 | 2023-2026 | 成熟期（企业向） | 内核态、低开销 | 特征明显、需自建 |

**S 曲线视角下的采购建议**：

- 处在"快速采纳期"的协议（Reality、TUIC/Hysteria2）**值得试，但不该是唯一依赖**。它们在理想网络下体验最好，在网络被针对性干扰时也最容易整体失效。
- 处在"成熟期"的协议（VLESS+WS/TLS、Trojan）**是所有场景的压舱石**，兼容性最好，出问题最容易排查。
- 处在"衰退期"的协议（SS、VMess）**只能作为兼容兜底**。如果你的机场 2026 年还在以 SS 为主力，这本身就是个信号。

## 2027 三情景推演：给不确定性留出仓位

单点预测几乎必然错。有用的做法是给出几个情景，并为每个情景标好"触发条件"和"我该做什么"。

### 情景 A：温和演进（基准，概率最高）

**特征**：监管偶有波动但不出重手；协议继续向 Reality/TUIC 迁移；通用档价格横盘；场景专线（游戏/回国/企业）继续细分溢价。
**触发信号**：跑道率维持 55%-70%；流量单价连续 3 月持平；头部套餐结构不变。
**行动**：主力放综合型老牌 + 年付锁价；场景需求单独配专线；备用 1 个即可。

### 情景 B：技术跃迁（乐观，概率中低）

**特征**：某类抗识别协议（如 Reality 后继）被客户端原生广泛支持，体验门槛骤降；老协议加速退场；新站凭技术差异化重新洗牌。
**触发信号**：Reality 类占比半年内从 25% 升到 50%+；主流客户端默认启用；新站平均跑道率回升到 70%+。
**行动**：不要急着追新协议，等"客户端默认支持 + 社区大规模验证"两个条件同时满足；届时时按月付试新站，成本极低。

### 情景 C：收缩与波动（悲观，概率中）

**特征**：监管趋严，部分线路频繁失效；机场数量收缩，长尾加速淘汰；解锁风控更严；价格不降反涨（供给减少）。
**触发信号**：跑道率跌破 50%；社区集中出现"某站失联"投诉；解锁可用率连续 2 周下降；头部套餐下调流量额度。
**行动**：主力必须是有明示政策 + 运营 ≥1 年的老牌；备用从 1 个提到 2 个（不同上游/不同地区）；年付比例下调，保留月付灵活性；把关键业务（收款、客户沟通）与"看剧娱乐"分账号隔离。

## 采购策略矩阵：不同情景下的动作表

把上面的情景落到具体动作，形成一张可以贴在桌面上的表。

| 你的画像 | 情景 A | 情景 B | 情景 C |
|---------|-------|-------|-------|
| 学生/省钱 | 年付锁通用档 | 保持，别为新技术加钱 | 月付，缩短决策周期 |
| 追剧/流媒体 | 标准档 + 年付 | 关注解锁稳定性再决定 | 保留 2 家可切换 |
| 游戏/联机 | 标准档 + UDP 优化 | 优先支持新协议的专线 | 备用线路必备（低延迟档） |
| 开发/技术 | 高级档 + 自定义规则 | 可试新协议做 A/B | 规则本地化，减少依赖 |
| 外贸/企业 | 高级档 + SLA | 关注新协议的企业支持 | 双供应商，合同短周期 |
| 家庭共享 | 高级档 + 软路由 | 保持架构不动 | 架构不变，增加备用订阅 |

**矩阵的读法**：纵向是你的身份（变化慢），横向是外部环境（变化快）。身份决定"买什么档"，环境决定"买多久、留几个备用"。绝大多数人的错误，是用身份去回答环境问题（"我是老用户所以继续年付"），或者用环境去否定身份（"行业不稳所以我不买了"）。

## 数据采集与复现说明（让别人也能验证你的结论）

一份趋势分析如果无法复现，它就只是观点。下面是最小可复现清单：

1. **样本定义**：候选池 15-30 个，必须包含 5 个运营 ≥1 年老牌 + 10 个新站 + 5 个专精站（游戏/回国/企业各至少 1 个）。
2. **采集频率**：跑道率与协议占比按季度；流量单价按月；解锁按周。
3. **采集口径**：单价一律换算成"元/GB（按标称流量）"，同时单独记录"按实际可用流量"的修正值，两个数都留着。
4. **数据落地**：JSON 快照 + 一份 CSV 汇总，放进 Git 仓库，每次采集只追加不改写历史。
5. **结论标注**：任何结论都要标注"样本量 / 观测窗口 / 采集日期"。没有这三项的数字，不要写进结论。
6. **反向检验**：每月挑一条自己最确信的结论，主动找反例。找不到反例的结论，通常是样本太小。

> 这三条最容易省，也最不该省：**样本量、观测窗口、采集日期**。行业分析里 90% 的错误结论，都源于把"一次测速"当成了"长期数据"。

## FAQ（趋势分析方法向）

**Q：我没有 30 个机场的候选池，还能做趋势判断吗？**
能，但要降低结论的强度。样本少于 5 个时，只做"单点观察"，不要做"趋势判断"。替代方案是直接看社区聚合数据（如导航站、评测站的历史文章），把它当作二手样本，但务必标注来源与时间。

**Q：跑道率统计会不会误判"换域名继续运营"的老站？**
会，这是该指标最大的漏洞。缓解方式：除了域名可用性，同时记录"页面标题/特征字符串"的哈希，域名换了但特征一致时手工合并记录。

**Q：协议占比怎么抽样才不失真？**
不要只抽头部机场（头部一定跟得最快），也不要只抽免费机场（一定最落后）。按"头部 1/3、腰部 1/3、长尾 1/3"分层抽样，各层按数量加权。

**Q：三情景推演的概率是我拍的吗？**
是主观概率，但必须有依据：基准情景权重最高（历史延续性最强），乐观/悲观各占较小权重。写清楚"什么信号出现就切换情景"，比纠结具体概率数字重要得多。

**Q：这份分析多久要重做一次？**
情景判断每季度复核一次；触发信号每周看一次；采购决策每月最多改一次（改太频繁本身就是成本）。
